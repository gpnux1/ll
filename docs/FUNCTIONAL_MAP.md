# 功能模块图谱 (原始架构推断)

> 方法: 全部 1058 个函数解析其引用的 RAM 全局(0x02/0x03 段) → 按"集中度"把全局分为
> 锚点型(≥70% 引用者集中在 0x4000 窗口, 定义模块)与服务型(跨模块引擎服务, 如 OAM/按键/主状态) →
> 仅用锚点型全局做 union-find 聚类 → 34 个功能群 (533 函数入群, 其余为单/双函数叶子)。
> 数据: `.scratch/ida/reports/functional_clusters2.json`
> 日期: 2026-08-31。**本文档是架构视图; 编译执行视图见 docs/modules/README.md。**

## 核心结论

> **2026-08-31 调用图修正 (plan)**: 用全量 callgraph 量化后发现原 F4-F7 边界有误, 修正如下:
> 1. **0x08044394-0x080446BC 不是"战斗"** — 这 8 个函数是对象/脚本共享的**全局状态服务**
>    (sub_8044514 被 78 个 0x8025xxx 对象生成函数调用; sub_804442C 被对象命令执行 801BE34/801C484 调用;
>    sub_804473C 被 MOD-06 hub sub_803F5B4 调用)。已并入 F5 对象系统。
> 2. **MOD-04+05 是同一系统** (场景对象 VM, 物理跨两个 .c 文件但语义一体)。
> 3. **调用图分层明确**: 引擎服务层 (F1/F2/F3/F9, 单向被调) ← 游戏逻辑层 (F5 对象 + F8 脚本 + F6/F7 剧情菜单,
>    相互调用 17+32 条边)。原"MOD-07=战斗"的推断证据不足, 0x080447xx-0x0804F0B8 实际含
>    对象行为函数族 (804C2FC/804C4D8=对象生成/命令, 804CEE0/804DD70=每帧分发, 8045F10=对象动画检查)。
> 4. **所有修正只改语义归属/文档, 不动函数物理顺序** (链接布局=ROM 布局, 不可动)。
> 5. **战斗主循环 = sub_80177AC** (用户确认: `gMainTasks[] = {Task_DispatchGameState, sub_80177AC}`,
>    gMainTaskSlot=1 时进入)。物理在 code_8010F10.c (MOD-03) 尾部, 语义重归属 **F7 战斗**。
>    调用 46 函数横跨 MOD-03/04/05/07 — 战斗是横切物理边界的功能模块。

### 调用图证据 (量测值)
- 0x08044-0F 段 237 函数中 18 个直接调用对象系统 (801A-8020); 对象系统 32 个函数调回
- sub_8044514 callers=78 (全为 0x08025xxx-26xxx), sub_80444A4 callers=84
- sub_8044414/4420/442C ← 801E040/801BE34/801C484 (对象命令执行)
- sub_804473C ← sub_803F5B4 (MOD-06 hub, 94 callers)

## 核心结论(原)

1. **原始工程的源文件 = 功能模块 = ROM 连续块**。除引擎群(服务型函数被各方调用)外,
   每个功能群 80-100% 落在一个连续地址段内 → 原作者大约 9 个 .c 文件按此顺序链接。
2. **泄漏驱动的 C 文件 拆分(code_1/1b/1c)不是功能边界** — 它在 0x08020D50/0x0804F0B8 两处
   把"场景对象"和"未知大区/战斗"切碎了; 功能边界由本图谱给出。
3. **脚本 VM 是独立模块** (0x0804F0B8-0x080533F0 ≈ code_804F0B8.c): 主循环 sub_8050014 +
   脚本初始化 sub_8052580 + opcode 处理器族 (sub_8052A38 一带, 含 0x8052C24-0x80532DC),
   聚类 100% 连续, 不与引擎混合。前面 0x080002A0 起的部分才是引擎。
