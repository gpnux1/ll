# 75% 之后：语义驱动的 GCC2.9 字节匹配路线

> 版本：2026-09-12  
> 目标：写出人类可读、全局变量和结构体命名合理、语义可信，并由 GBA 时代 GCC2.9 风格编译出与原 ROM 完全一致字节的 C 代码。

## 1. 现在真正要解决的问题

项目已经完成约 75% 的函数字节匹配，但剩余函数大多是中大型函数。当前瓶颈不是单纯缺少 permuter 实验，而是：

- 已匹配代码的变量、结构体、全局变量和功能命名仍可能不正确；
- 未匹配函数缺少稳定的参数、返回值、状态和数据结构模型；
- C 文件名和 module 标签可能只是历史分组，不能代表功能边界；
- 大量逻辑由脚本触发，但真正执行动作的是地图、角色、对象、战斗、UI、VBlank 和资源引擎；
- GCC2.9 的声明顺序、类型提升、寄存器 home、栈槽和共享尾块会影响最终字节。

所以正确的目标不是“先语义、后匹配”两个割裂阶段，而是一个闭环：

```text
原始 ROM/ASM + 调用图
    -> 语义、状态、全局和结构体建模
    -> 合理命名
    -> 人类可读的 C
    -> GCC2.9 生成形状调整
    -> bytecmp/fncheck
    -> 合入和全量验证
```

语义分析服务于最终 C；匹配验证 C；命名和可读性决定交付质量。

## 2. 零信任，但不能放弃命名

默认不相信以下内容的语义：

- `src/*.c` 文件名和 `functions.tsv` 的 `module`；
- 函数名、全局变量名、结构体名、字段名和注释；
- 旧功能图谱、模块文档、家族文档和路线文档；
- 其他 agent 的分析、候选和原型；
- 旧脚本 opcode/authoring 表。

它们只能帮助搜索。命名不是禁止事项，而是需要证据驱动的工作目标。名称应从以下证据逐步提升：

- **地址名**：尚未定性；
- **临时描述**：例如 `global_03000E70`、`field_B0`、`state_value`；
- **局部语义名**：一个函数或一个调用子图内证据充分；
- **公共语义名**：至少两个独立消费者支持，且没有冲突；
- **正式名称**：调用图、数据流、运行时和字节匹配均没有已知矛盾。

如果旧名称与新证据冲突，保留地址和字节结果，修正名称并记录原因。不要为了保留旧文档而迁就错误命名，也不要因为不确定就永远拒绝建立更好的模型。

## 3. 证据优先级

1. **E0：原始数据**：`baserom.gba` 字节、原始资源、表、函数指针、任务表、对象表和脚本正文。
2. **E1：按地址生成的 ASM**：控制流、直接调用、寄存器/栈参数、访存宽度和跳转表。
3. **E2：调用图交叉证据**：多个调用者/消费者对同一参数、字段、状态和返回值的一致使用。
4. **E3：运行时交叉证据**：模拟器、调试器、受控执行、脚本样本和跨帧观察。
5. **H：历史资料**：只用于定位搜索位置，不能单独支持命名、原型、结构体或功能边界。

每个重要命名都要说明依据等级。没有 E2 时，优先保留地址视图或 `field_XX`，不要急于创建公共结构体。

## 4. 调用图是主线，脚本是上下文

从 ROM/ASM 重新建立五类调用图根：

1. 普通 `bl` 直接调用；
2. 主循环、任务槽和游戏状态表；
3. VBlank、中断、DMA、LZ、输入和显示管线；
4. 对象、行为、命令和状态处理器表；
5. 脚本 opcode handler 表和脚本 VM。

脚本驱动大量流程，但脚本 handler 往往只是请求服务或改变状态。地图加载、角色移动、对白窗口、对象行为、战斗回合、VBlank 上传和资源解压仍需按实际调用图分析。

脚本只在需要时补充：

- 哪个 handler 进入当前引擎函数；
- 参数来自哪个脚本字段；
- 返回值是否表示等待或异步请求；
- 哪个跨帧状态由下一帧任务或 VBlank 消费。

不能因为函数被脚本触发就把它叫作脚本 VM，也不能因为不在 opcode 表就跳过语义分析。

## 5. 每个函数都建立函数卡

已匹配函数和未匹配函数都要分析。每个函数卡至少包含：

```text
address:
current_name: 当前检索标签，不代表正确语义
physical_tu: 当前物理 C 文件，不代表功能模块
match_status: 0/1
entry_kind: direct / task-table / vblank / object-table / opcode / unknown
callers: 地址和调用点
callees: 地址和传参
indirect_tables: 表地址、槽位和目标
args: 寄存器/栈位置、宽度、用途
return: 返回寄存器/标志、调用者用途
memory_reads: 地址/偏移、宽度、条件
memory_writes: 地址/偏移、宽度、条件
persistent_state: 跨帧地址、宽度、初始化和清理
state_transitions: 状态值、进入条件、写回值、下一状态
script_relation: none / called-by-script / changes-script-state / unknown
semantic_name: 当前最佳语义名及证据等级
uncertainty: 尚未证实的部分
```

函数卡先回答“机器做了什么”，再回答“它可能叫什么”。

## 6. 全局变量和结构体的建模顺序

### 6.1 全局变量

对每个全局地址记录：

- 所有读者和写者；
- 访问宽度；
- 读写条件；
- 初始化、每帧更新、清理和销毁路径；
- 是否跨任务、跨状态或跨 VBlank 生命周期；
- 是否由脚本 handler 写入或消费；
- 与相邻地址是否确实属于同一数据块。

先使用 `global_XXXXXXXX`，当多个消费者一致后再给语义名。不要仅凭相邻地址或一个函数的变量名合并全局。

### 6.2 结构体和对象

先建立偏移表：

```text
offset | width | read/write | functions | observed values | confidence
```

只有以下条件满足时才提升为字段名：

- 多个函数访问同一偏移；
- 宽度和读写方向一致或差异可解释；
- 调用者传入的对象指针一致；
- 字段在初始化、更新和清理路径中有连贯作用。

结构体视图必须保持与 GCC2.9 所需字节形状兼容。必要时保留裸字节/半字视图，并为语义分析建立旁注，而不是强行把所有访问改成高层字段。

## 7. 语义和匹配的实际循环

### 7.1 先分析当前函数

从当前 ASM、ROM 和调用点确定控制流、机器契约和数据访问，写入函数卡。调用图不足时，追踪上游调用者、下游消费者和间接表。

### 7.2 再写可读 C

在候选目录中写自然 C：

- 命名反映已验证数据流；
- 未知字段保持保守；
- 控制流与状态机清楚；
- 不引入错误原型、错误指针步长、无界索引或伪造数据流；
- 代码即使暂时不匹配，也应能被人审阅。

### 7.3 最后调整 GCC2.9 形状

在语义正确、命名合理的 C 上研究：

- 局部声明顺序；
- 变量跨 basic block 的生命周期；
- `u8/u16/s32` 和整数提升；
- 条件极性和 switch 源码顺序；
- 指针算术与字节偏移；
- 结构体字段访问和裸偏移的选择；
- home/栈槽、callee-saved 寄存器、S-bit；
- 字面池、跳转表和共享尾块。

每次尽量只改变一个因素。permuter 只是搜索工具，分数不是证明。不能为了分数牺牲可读性或语义。

### 7.4 字节验证

```bash
scripts/fndiff.sh <当前函数名> <候选.c>
scripts/bytecmp.sh <当前函数名> <候选.c> "sym = 0x...;"
```

只有 byte-exact 且人工审查通过，才替换真实 `src` 中的 `INCLUDE_ASM`，然后运行 `fncheck.py`。头文件、原型、公共结构体、`iwram.h` 或 `linker.ld` 变化后必须强制重编。

## 8. 优先级

不按 C 文件名或旧模块名排序，而按语义杠杆排序：

1. 调用图根、任务表、对象表和 VBlank 管线；
2. fan-in 高且被多个状态机共享的引擎枢纽；
3. 共享状态块和对象结构体的读写者；
4. 已匹配但命名/原型/字段会污染多个消费者的函数；
5. 机器契约已经稳定、只剩 GCC2.9 形状的未匹配函数；
6. 依赖多个未知全局和大型状态机的函数。

脚本相关函数的优先级取决于它能否解释某个引擎子图，不取决于它名字里是否有 `script`。

## 9. 卡点处理

当函数卡住时，先判断卡点属于：

- 调用约定未确认；
- 间接调度表未确认；
- 全局或结构体布局未确认；
- 状态生命周期或下一帧消费者未确认；
- 可读 C 的语义仍有冲突；
- GCC2.9 声明顺序、类型提升、home 或寄存器分配差异；
- 候选和当前编译单元/符号环境不一致。

连续两轮实验没有缩小差异时，保存当前人类可读候选，记录精确差异和下一条实验，转交同一调用子图的另一个函数。不要无限调参，不要把低分当成功。

## 10. 多 Agent 交接

工作包必须以以下内容定义：

```text
package_id
function addresses
entry/table roots
callers and callees
shared globals/fields
state and cross-frame consumers
current readable C/candidate
exact byte difference
first unresolved issue
next experiment
shared-file impact
```

一个工作包可以跨多个 C 文件，但不允许多个 agent 同时修改同一函数。源码文件名只是物理位置，不是任务边界。

交接文件放在版本控制的 `docs/handoffs/<package_id>.md`。重要内容不能只放在 `.claims/`、`permuter/` 或 `.scratch/`。

后继者必须：

1. 记录当前 `git status`；
2. 按地址重新核对 ROM、ASM、调用点和当前源码；
3. 阅读 handoff，但重新验证旧结论；
4. 重现候选或分析命令；
5. 从第一处未解决问题继续；
6. 交付时追加恢复记录，不覆盖前任事实。

## 11. 两周执行建议

### 第 1-2 天：调用图和队列

- 从 ROM/ASM 重新统计直接调用、间接表项和 fan-in；
- 把当前 module 只当物理标签；
- 为已匹配和未匹配函数建立优先级；
- 标出旧命名与机器证据冲突的高影响函数。

### 第 3-6 天：高扇入引擎枢纽

- 选择 1-2 个重新计算后 fan-in 高的枢纽；
- 建立所有调用者分组、参数/返回值和全局读写表；
- 识别状态块、对象记录和跨帧消费者；
- 写出一组可读 C 或明确的未匹配机器契约。

### 第 7-10 天：数据模型和姊妹函数

- 沿同一调用子图分析结构体字段和全局生命周期；
- 交叉检查已匹配姊妹函数的命名和原型；
- 选择机器契约稳定的函数进行 C 候选和字节匹配；
- 将匹配结果回填调用图和数据模型。

### 第 11-14 天：扩大子图和交接

- 沿高影响调用边扩展到下一个服务或状态机；
- 对反复卡在 GCC2.9 形状的函数形成可复用实验记录；
- 生成完整 handoff，释放或明确转交锁；
- 根据新增证据重新排序下一轮。

## 12. 完成标准

每个函数不是“分析过”就完成，而是达到以下某种明确状态：

- **MATCHED**：语义合理、命名经过证据检查、C 可读，并通过 bytecmp/fncheck；
- **READY-HANDOFF**：函数卡、调用子图、可读候选、精确差异和下一实验齐全；
- **BLOCKED**：明确缺少哪个外部证据或共享接口，并已保存当前结果。

每轮同时统计：

```text
新增字节匹配数
已完成函数卡数
已验证调用边数
已交叉验证全局/结构体字段数
已修正的高影响错误命名数
可复现交接包数
```

最终交付的标准始终是同一个：**人能读懂、命名合理、语义不自相矛盾，并且 GCC2.9 风格编译后与原 ROM 字节一致。**
