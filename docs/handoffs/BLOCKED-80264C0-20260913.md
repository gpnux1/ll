## 卡点: GCC2.9 寄存器分配墙
候选 `permuter/sub_80264C0/base.c` 逻辑与目标逐块对应, 但**序言/全局分配不同**:

| | 目标 | 候选 |
|---|---|---|
| 高寄存器保存 | `push {r6,r7}` (r8 + sb) | `push {r7}` (r8) |
| obj/arg1 | r6 / r7 | r5 / r6 |
| rec | r5 | r7 |
| result | **sb** | **r8** |

- 目标: `result→sb`, case1 把 `&gUnk_03000825` 提升到 `r8` (跨 sub_801768C 调用存活)。
- 候选: `result→r8`, case1 的 g8625 走池载, 不提升。
- 该分配差导致 jump table 基址偏 2B、全函数偏移, bytecmp 1060B。

### 已排除实验
- `result` 先/后声明 (rec 前/后): 无改善。
- `result` 类型 `u32` / `int` / `u8`; `rec` 类型 `SlotRec*` / `u8*` / 直接数组表达式: 均 1060 或以差。
- 显式 `u8 *pcnt = &gUnk_03000825;` 在 case1/2 用 `(*pcnt)`: 更差 (1123B) — 被优化回。
- 不提升 `rec` (每处直接 `gUnk_083988A8[obj->slot]`): 1154B。

### 下一步建议
1. 用 permuter 以 `base.c` 为种子跑全局分配搜索 (目标态: 结果入 sb / g8625 入 r8)。
2. 或试在 case1 里用一种"强制地址跨调用存活"的写法, 让 GCC 把 `&g8625` 分到 r8,
   自然把 result 挤到 sb。
3. 姊妹: `sub_802DFDC`(u32 返回, 单参) 已匹配, 可对照其 result 变量声明位置。
