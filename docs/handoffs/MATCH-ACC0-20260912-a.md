## C. 用户候选的语义偏差 (重要)

用户提供的候选把循环读写成了 `gUnk_0839B462[count] == 0xF00` —— 按 ASM
(E1/E2), 读索引是 **i** (r1), 不是 count (r3): `ldrh r0,[r5 + r1*2]`。
按 count 索引且 count 只在命中时前进, 若首项非 0xF00 会死循环。
合入版已修正为 `base[i]`。

## D. 自然风格 vs 字节匹配的实证边界 (本次用 permuter + bytecmp 系统性排除)

用户要求尝试"2006 年人类风格"(自然 `count++`、`&table[i]`) 并用 permuter 压分。
实测结论 (全部有 bytecmp/反汇编证据):

1. **u16 计数器必败**: `u16 count/i` 无论声明顺序 (测 8 种排列)、有无
   `u8 arg` 局部、初始化方式, 一律 count→r2 / arg→r0 + 多一条 `adds r3,r0,#0`
   拷贝; 目标是 count→r3 / arg→r2 无拷贝。u32 + 显式 `(u16)(x+1)` 是唯一路径。
2. **permuter 独立再发现了 arg 截断效应**: 从自然版 (score 455) 爬到 70
   (约 9000 迭代后平台), 它在 while 条件里塞 `new_var = arg0` (u8 内嵌赋值)
   使分配全对 —— 但 lsrs r2 被调度到函数最前 (守卫先读 arg0, CSE 提前),
   目标要求 movs,movs,lsrs,ldr 序。声明初始化形式 (`u8 arg = arg0;`) 调度对
   而分配错。u16 下两头不可兼得, 8000+ 迭代无解 = 编译器结构性墙。
3. **尾部指针加法序再次确认 (经验 2/77)**: `&table[i]` → `adds r4,r6,r0`
   (基址在前, GCC 指针和规范化); 目标 `adds r4,r0,r6` 只能由纯整数加法
   `(u16*)((u32)i*2+(u32)table)` 按源码序生成。
4. **extern 符号与字面量字节等价**: `table = gUnk_0839B462` 与
   `table = (u16*)0x0839B462` 生成完全相同代码 (SYMBOL_REF 同址);
   bytecmp(施加池重定位) 验证通过。
