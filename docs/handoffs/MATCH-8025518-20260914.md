## 2. 语义建模与业务功能
该函数是标准 GBA OAM 精灵属性配置与图块槽推进工具函数：
1. **入参**:
   - `out`: 目标 `OamData *` 结构指针（由调用者如 `sub_802192C` 传入 `&gOamBuffer[idx]`）
   - `x`, `y`: 精灵在屏幕上的坐标（分别写入 `oam.HPos` 和 `oam.VPos`）
   - `tileNum`: 精灵使用的起始图块编号（写入 `oam.CharNo`）
   - `shape`: 精灵形状（0 = 方形, 1 = 宽矩形, 2 = 高矩形，写入 `oam.Shape`）
   - `size`: 精灵尺寸档位（0..3，写入 `oam.Size`）
   - `pal`: 调色板索引增量（基底为 13，即 `oam.Pltt = pal + 13`）
2. **结构体组装**:
   配置默认属性：`AffineMode = 0`, `ObjMode = 0`, `Mosaic = 0`, `ColorMode = 0`, `AffineParamNo_L = 0`, `HFlip = 0`, `VFlip = 0`, `Priority = 0`。
3. **结构体输出**:
   `*out = oam;` 将组装好的 8 字节 `OamData` 拷贝至目标缓冲区。
4. **图块偏移查表与返回值**:
   `gUnk_08393A30` 为形状/尺寸对应的图块占用数表（`tileCount`）。
   `return (u16)(tileNum + gUnk_08393A30[size + shape * 4]);`
   返回分配该精灵后的下一个可用图块编号。

## 3. 破局关键（推翻旧假设）
- **历史误区**: 历史记录（progress.md 2026-09-04 与 EXPERIENCE 规则 139）认为位域结构体会导致寄存器提升无法逐字段写回栈，因而引入了复杂的 `union { struct S s; u32 w[2]; } u;` 与字段别名，导致后续寄存器分配与写回次数陷入死锁。
- **真相与突破**:
  直接声明局部变量 `OamData oam;`，逐字段位域赋值，并在末尾执行结构体拷贝 `*out = oam;`。GCC 2.9 在编译未初始化的位域结构体赋值与结构拷贝时，自然会在栈上逐位域写回 `[sp]` 与 `[sp+4]`，并生成标准的 `ldr r4, [sp]; ldr r5, [sp+4]; str r4, [r0]; str r5, [r0+4]`！
  在表索引计算上，原汇编中 `add sb, sl` 是由 `[size + shape * 4]` 生成，该表达式使得 `arg4`（`shape`）分配到 `sl`，`arg5`（`size`）分配到 `sb`，公用掩码 `0xFFFFF3FF` 分配到 `r8`，完美化解历史记录中困扰已久的 global-alloc 互换卡点！
