## 2. 功能语义

在 `obj->equipSlots` (6 个装备槽, +0x8D..0x92) 里找第一个属性命中的槽下标:
`sub_804DD90(槽值, arg1) == arg2` 命中则返回槽下标 0-5, 否则 -1。
仅玩家侧对象 (`slot <= 0xA`) 生效; 敌方/特效对象直接返回 -1。

调用点传入的 (arg1, arg2) 组合: (2,6)/(2,7)/(2,8) 与 (3,1)/(3,2)。
`sub_804DD90(id, sel)` 从 `gUnk_087EA580[id*12+10]` 指向的 3 字节属性块里取
sel 指定的位段, 所以本函数整体语义 = "该对象是否携带某个特定属性值的装备"。

## 4. 形状关键 (GCC 2.95)

| 写法 | 结果 |
|---|---|
| `values = (u8 *)obj + 0x8D;` | 基准 (原代码, 128B) |
| `values = obj->equipSlots;` | **字节一致 (128B)** ✅ |
| `obj->equipSlots[i]` 逐字段 + `obj->pad_93[i]` | 差 95B, 多出 8B (136B) ❌ |

基址必须**整块赋给一个指针**, 让 agbcc 折成目标里的
`adds r5, r3, #0` / `adds r5, #0x8d` 两条。逐字段访问时 agbcc 对每个字段
独立重算地址 (`adds r0, r3, #0` / `adds r0, #0x8c` / `ldr r0, [...]` ...),
8 个字段 = 8 组地址计算, 还退化成 4 字节 `ldr`。与 `battle_engine.c:784`
记录的 Sub6C 坑同源: 结构体字段访问不会自动共享基址寄存器。

## 5. 剩余的 ROM 怪癖 (有意保留)

前置过滤读 **8 字节** (+0x8D..0x94), 但循环只扫 **6 个槽** (i <= 5)。
多读的 +0x93/+0x94 是 `pad_93[6]` 的前 2 字节, 全 ROM 无任何写入点
(code.s 全量反汇编里 `#0x93`/`#0x94` 仅 7 处出现, 全是次数计数
(`0x93<<5`、`0x94<<1`) 或从常量基址取 ROM 表的偏移; `#0x92` 的 6 处
消费者 sub_80457AC/8045BF4/8048B5C/BattleFxObjs_Add/804F0B8 全是
`ldrb` 读, 无 `adds #0x92` + `adds #1` 的间接写), 恒为 0, 所以该检查
无实际影响 —— 它是原代码的过宽过滤 (或复制粘贴残留)。
为保持字节一致, C 侧保留 8 个 `!= 0` 判据, `values[6]/[7]` 越过
`equipSlots[6]` 末尾 2 字节 (agbcc 无 -Warray-bounds, 无告警)。
