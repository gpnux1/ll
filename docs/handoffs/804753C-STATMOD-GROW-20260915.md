## 3. 语义模型 (已验证事实 + 强推断)
按 `kind` 选一个战斗属性修正槽 `statMods[kind]`，把它按 `amount`% 增长，但设一个上限：
只有当当前修正值 `cur` 低于 "参考属性的一半" 时才增长。

- `cap = (u16)(((u16)(refStat / 10)) * 5)`  ≈ refStat 的 50%（整数 `/10*5`，两次 u16 截断）。
- `add = (u32)((float)base * ((float)amount / 100.0f))`（`__fixunssfsi` 向零截断）。
- 若 `cur < cap`：`statMods[kind] = (u16)(cur + add)`。

kind→字段映射 (E2，与已匹配 `sub_8046F0C` case5-9 的 `stats[i] + statMods[i]` 配对同源):

| kind | base(乘数) | cap 参考 | 目标 statMods | 额外 |
|------|-----------|----------|---------------|------|
| 0 | atc (0x74) | atc (0x74) | statMods[0] (0x7E) | 另写 `0x0300090A = (u8)(cur+add)` |
| 1 | def (0x76) | **atc (0x74)** | statMods[1] (0x80) | cap 源与 base 源不同 → 单独代码路径 |
| 2 | agl (0x78) | agl (0x78) | statMods[2] (0x82) | |
| 3 | men (0x7A) | men (0x7A) | statMods[3] (0x84) | |
| 4 | res (0x7C) | res (0x7C) | statMods[4] (0x86) | |

- **kind==1 的异常 (已验证事实, E1)**: cap 读 `obj->atc`(+0x74) 而 base 读 `obj->def`(+0x76)。
  这是原 ROM 的真实行为（asm 明确 `adds r0,#0x74` 算 cap、`ldrsh [obj+0x76]` 算 base），
  也正是 case1 无法复用 case2-4 共享 prologue、必须单独 `ldrsh`+提前 `bhs` 检查的原因。
- **kind==0 的异常 (已验证事实, E1)**: 唯一写 `0x0300090A` 的分支，且其 float 尾块被内联复制
  （asm 中 case0 有独立 float 序列，与共享 `_08047686` 重复）。
- **工作假设 (未定)**: 具体游戏机制（"战斗中按帧累积的属性 buff/蓄力"）与 `0x0300090A` 的用途
  （全 ROM 仅此函数写、无读者 → 疑似调试/上一帧快照 scratch）。`gFxReqFrames` 在此被当百分比用，
  与其历史名 "Frames" 不符，属既有命名待复核项。

- 声明顺序重排 (mod/cur/base/cap/add 各种序)：无效。
- 单加载共享 (case0/2/3/4 用同一 `base` 变量算 cap 与 float)：无效。
- `s16 base` / `u16 base`：无效。
- 复制 `u8 amt = amount;` 早物化：无效。
- 乘数操作数顺序交换 `(float)amount/100 * (float)base`：无效。
- 尾块不重赋 `cur`、直接 `*mod=(u16)(*mod+add)`：body 长度偶合到 416 但 mov 仍在，差 262。
- 顶层 `mod = obj->statMods` 早用 obj：obj 成功进 r4，但引入额外 `adds r7,r4,#0x7e` 且 amount 仍 r8。
