## 2. 机器契约与语义建模
该函数是战斗引擎中用于根据属性掩码对活动敌方战斗槽位进行筛选的例程。它遍历敌方对象槽位 (5..11)，收集状态判定为活动 (`sub_8045F10 == 2`) 的槽位，再依据战斗对象的 `pad_AC[0]` 属性位掩码与源对象匹配的条件，将符合条件的敌方槽位输出到指定数组中并返回数量。

### 2.1 依赖关系与生命周期
- **对象池模型**:
  - `GetObjPool()`: 获取战斗对象池首地址 (0x02037028)。
  - 战斗对象结构体 `BattleObj` (步长 `0xC8 = 200` 字节):
    - 槽位 0..4: 玩家队伍 (5 槽)。
    - 槽位 5..11: 敌方单位 (7 槽)。
  - `pad_AC[0]`: 阵营 / 队伍 / 属性标识字节。
- **被调子函数**:
  - `GetObjPool()`: 获取对象池基地址。
  - `sub_8045F10(BattleObj *obj, u16 mask)`: 检查对象生存状态与目标可选性 (返回 2 表示活动且可选)。

### 2.2 核心业务逻辑
```c
u8 sub_804621C(BattleObj *obj, u8 *outSlots, u8 mask)
{
    u8 localSlots[12];
    u8 *buf;
    BattleObj *pool;
    u8 targetVal;
    u8 count;
    u8 outCount;
    u8 i;
    u8 j;
    u8 endSlot = 12;

    targetVal = obj->pad_AC[0] & mask;
    pool = (BattleObj *)GetObjPool();

    for (j = 0; j <= 6; j++)
        outSlots[j] = 0;

    buf = localSlots;
    count = 0;
    for (i = 0; i <= 6; i++)
        buf[i] = 0;

    i = 5;
    do {
        if (sub_8045F10(&pool[i], 0x1FF) == 2) {
            buf[count] = i;
            count++;
        }
        i++;
    } while (i < endSlot);

    i = count;
    outCount = 0;
    for (j = 0; j < i; j++) {
        if ((pool[localSlots[j]].pad_AC[0] & mask) == targetVal) {
            outSlots[outCount] = localSlots[j];
            outCount++;
        }
    }
    return outCount;
}
```

## 3. 破局关键与 GCC 2.9 特征

### 3.1 前期历史卡点回顾 (EXPERIENCE.md 2026-09-06)
前人探索在此函数遇到两个看似无法攻克的深层死结并挂起：
1. **高位寄存器错位**: 目标推栈 3 个高寄存器 (`push {r5, r6, r7}` 分别对应 `r8/sb/sl`)，将 `pool` 放在 `r7`，长命变量 `targetVal(filtered)` 放在 `r8`，`outSlots` 放在 `sb`，`mask` 放在 `sl`。而此前所有尝试均少用一个高寄存器，导致所有变量整体向低位寄存器偏移（`filtered` 掉入 `r7`，`pool` 掉入 `r6`）。
2. **循环条件折叠死结**: 目标汇编循环 3 结尾是 `cmp r4, #0xc; blo _0804626C`（即 `cmp #12; bcc`）。此前尝试了 30+ 种循环写法，GCC 2.9 (agbcc) 均在 `fold-const.c` 前端将 `u8 i < 12` 强制折叠规范化为 `i <= 11`，进而发射 `cmp r4, #0xb; bls`。

### 3.2 真正机制揭秘与破局

#### 3.2.1 局部指针 `buf = localSlots` 锁定 `r6` 消除寄存器错位
通过仔细对比目标汇编，发现目标在循环 2 与循环 3 中：
`r6` 始终保存栈帧指针 `sp`（即 `localSlots` 缓冲区基址），并且 **跨越了 `sub_8045F10` 的函数调用**：
```arm
64:   adds r0, r6, r5
66:   strb r4, [r0, #0]
```
在直接使用数组形式 `localSlots[count] = i;` 时，GCC 认为 `sp` 随时可重载，因此未将栈地址放入 callee-saved 寄存器。引入显式指针变量 `buf = localSlots;` 后：
- `buf` 必须在寄存器中保活，因此占满了 Thumb 的全部 4 个低位 callee-saved 寄存器：
  - `r4`: 循环索引 `i`
  - `r5`: 收集计数 `count`
  - `r6`: 局部缓冲指针 `buf`
  - `r7`: 对象池指针 `pool`
- 此时低位寄存器已被完全耗尽，其余 3 个跨调用长寿命变量 `targetVal`、`outSlots`、`mask` 被迫分配至 `r8`、`sb(r9)`、`sl(r10)`。
- 由此完美复现 `push {r5, r6, r7}` (对应保存 r8, sb, sl) 以及 `mov r8, r1`、`mov sb, r1`、`mov sl, r2` 的完整寄存器分配布局！

#### 3.2.2 命名变量 `endSlot = 12` 阻断常量折叠
深入 GCC 2.9 源码（`tools/agbcc/gcc/fold-const.c:5873`）分析：
- GCC 前端只有在遇到 `TREE_CODE(arg1) == INTEGER_CST` 且 `arg1 > 0` 时，才会在语法树层面将 `LT_EXPR` 转换为 `LE_EXPR`（`i < 12` -> `i <= 11`）。
- 若在函数内声明局部变量 `u8 endSlot = 12;`，语法树中的操作数是 `VAR_DECL` 而非 `INTEGER_CST`，`fold-const.c` 不会做 `<= 11` 的转换，保留 `LT_EXPR`。
- 在后续的代码生成与寄存器分配中，因所有高低位寄存器已被占满，GCC 在循环条件比较时直接将已知常数值以立即数形式物化到指令中，发射 `cmp r4, #0xc; blo`！
- 配合 `do { ... } while (i < endSlot);`，消除了循环入口的多余守卫跳转，使整个循环区段 100% 字节精确匹配。

#### 3.2.3 计数器变量复用 `i = count` 对齐第四循环
在第四个循环前添加 `i = count;`，使 `r4` 立即复用存放循环上限，释放出 `r5` 用于常驻存储结构体步长 `0xC8` (`movs r5, #0xc8`)，并使内部重载 `mov r6, sp`，完美闭环最后 40 字节指令流。
