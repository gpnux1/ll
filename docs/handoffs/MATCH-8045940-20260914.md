## 2. 完整语义与业务逻辑

本函数用于在战斗中按当前角色的类别/槽位类型（`obj->slot`，`0..7`），从其装备的 8 个技能（`obj->skills[0..7]`）中过滤出允许施展的技能，并将符合条件的技能索引 `i` 收集进输出缓冲 `buf`。

1. **初始化**: 清空 `buf[0..7] = 0`，初始化计数器 `count = 0`。
2. **8 槽循环**: 遍历槽位 `i = 0..7`:
   - 调用 `sub_80488CC(obj, obj->skills[i])` 检查技能是否可用或 MP 足够，若返回 `0xFF` 则跳过该技能。
3. **按角色类别外层分派 (`switch (obj->slot)`)**:
   - `case 0, 1, 6, 7`: 直接接收所有可用技能，执行 `buf[count++] = i`。
   - `case 2`: 内层按技能 ID 分派，仅接收技能 ID 为 `8` 或 `13 (0xD)` 的技能。
   - `case 3`: 仅接收技能 ID 在 `[14, 16] (0x0E..0x10)` 范围内的技能。
   - `case 4`: 仅接收技能 ID 在 `[22, 24] (0x16..0x18)` 或 `[26, 28] (0x1A..0x1C)` 范围内的技能。
   - `case 5`: 仅接收技能 ID 在 `[30, 31] (0x1E..0x1F)` 或 `33 (0x21)` 的技能。
4. **返回**: 返回收集到的有效技能总数 `count`。

## 3. 破解两大历史卡点 (从 2026-09-04 挂起至今)

前任分析（2026-09-04，claude-45940）记录了两大死锁卡点：

### 卡点①：ldrb 后的有符号比较 (bgt/blt) 与常数形式
- **旧误判**: 认为是 `if (skill > 0x10) break; if (skill < 0xE) break;`。但 GCC 2.9 的 `combine.c:simplify_comparison` 会在 `LT` 操作数大于 0 时强制转换为 `LE (C - 1)`，导致 `< 14` 恒被编译为 `cmp #13; ble/bls`，永远出不来目标的 `cmp #14; blt`。
- **破解**: **内层根本不是 `if` 语句，而是嵌套的 `switch (obj->skills[i])`**！
  GCC 2.9 的 `stmt.c` 在为小 case 集生成二叉比较决策树时，对于连续区间 `case 0xE: case 0xF: case 0x10:` 会自然生成：
  ```arm
  cmp r0, #0x10
  bgt reject
  cmp r0, #0xe
  blt reject
  ```
  这与 target 汇编中的 `bgt 0x10`、`blt 0x0E`、`blt 0x16`、`ble 0x18`、`bgt 0x1C`、`blt 0x1A`、`blt 0x1E`、`ble 0x1F`、`bne 0x21` 100% 逐条完全吻合！

### 卡点②：`count` 与 `i` 的 `r4 ↔ r5` 互换
- **旧误判**: `count` 设为 `u8` 时，由于第一循环与第二循环均使用 `i`，导致 `pri(i) = 9677` 始终压过 `pri(count) = 9638`（差 39 分），`i` 抢占 `r4`，`count` 沦落至 `r5`。
- **破解**: 在外层 switch 的 `case 0, 1, 6, 7` 中，原作者并未写成共享 break 的 fallthrough，而是**每个 case 各自分立书写 `buf[count] = i; count++; break;`**！
  - 这使 `count` 的有效引用数增加了 6 次（`refs` 从 32 提升至 38），优先级 $\text{pri}(count)$ 跃升至 11,000+，成功压过 $\text{pri}(i)$！
  - `global-alloc` 顺理成章地将首个可用寄存器 `r4` 分配给 `count`，`r5` 分配给 `i`。
  - 同时，GCC 2.9 的 `jump.c` 交叉跳转合并（cross-jumping pass）自动将这 4 处完全相同的写缓冲区块与内层 switch 的命中块统统合并到 `_080459F2`，跳转表项 0、1、6、7 均精确指向该单一标签，与原 ROM 字节逐位全等！
