## 2. 功能语义 (E2 级证据)

为战斗对象装配**一条 32×8 OBJ 精灵条目**写入 `gOamBuffer[index]`, 返回 `index - 1`。

- **调色板槽选择**: `kindFlags & 0x8000` (= ObjHead.scriptPtr 语义中"激活后清除"的位, 见
  `ObjHead.kindFlags` 注释; 这里表现为"图形/调色板装载已完成") 置位时用 `headA.f_2F`
  (+0x2F, `f_2F` 的既有语义就是"装载完成后回填 +0x29 的最终值"), 否则用 `headA.palSlot` (+0x29,
  装配前由 sub_801D12C 指定)。二者都是 u8, 拼进 16 位属性字高 4 位之前被 `<<4` 提升,
  与目标 `mov r1,r9; lsls r2,r1,#4; movs r1,#0xf; ands r0,r1; orrs r0,r2` 完全吻合。
- **字段赋值** (`GameOamData.fields` 位域视图):
  `VPos = posY - 5`, `AffineMode = 0`, `ObjMode = (kindFlags & 0x10) ? 1 : 0`, `Mosaic = 0`,
  `ColorMode = 0`, `Shape = 1`, `HPos = posX - 0x10`, `AffineParamNo_L = 0`, `HFlip = 0`,
  `VFlip = 0`, `Size = 1`, `CharNo = slot <= 0xA ? 0x140 : 0x12E`, `Priority = 3`, `Pltt = pal`。
- `Shape = 1` / `Size = 1` → 32×8 精灵; `Priority = 3` (显示优先级 3, 高于 D214 的 2);
  `CharNo` 按槽号是否玩家侧 (≤0xA) 选 tile 基号 (0x140 vs 0x12E, 即 2 个 8×8 tile 的 32×8 块)。
- 与 `sub_801D214` 同为 gOamBuffer 逐条装配; 与已匹配的 `sub_801D984` 同构 (后者数据源是
  `gUnk_03000670` 弹出项表, 本函数数据源是 `BattleObj->headA` 图形头)。

## 3. 破局关键与 GCC2.9 匹配经验

前任 agent (zcode-ll2, 2026-09-06) 已把结构解到 "100%", 但卡在**寄存器 home 分配 tie**
(attr 高位 vs 低位)。本次在 `sub_801D214` 匹配经验 (位域结构体 + 逐字段赋值) 的指引下改用
`GameOamData` 位域视图一次成型。三处决定性细节:

1. **位域视图替代手写掩码链**: 用 `o->fields.* = ...` 逐字段赋值, GCC2.9 自动展开成
   目标里那串 `movs/negs/ands/orrs` 连续掩码。前任手写 `~3 / ~0xC / ~0x10 / ~0x20` 的
   裸 u8 掩码链虽然形状接近 (score 850..1150), 但局部变量 home 无法收敛。
   **注**: 目标中 `subs r0,#0xe` 是 GCC2 对 `~0xE` 的物化 (复用已有 `r0=1`), 不是源码里的减法。

2. **`ObjMode` 必须写成布尔式**: `(kindFlags & 0x10) ? 1 : 0` (或 `!= 0` / `!!(...)`) 让 GCC2
   先物化常量 `r0 = 1`, ObjMode 的 `& ~0xE` (即 `~0xD`) 部分复用该寄存器 → 生成 `subs r0, #0xe`。
   若写成 `(kindFlags >> 4) & 1`, 常量变成 `#13` → 额外 `movs r0,#13; negs r0,r0`, 函数变 244 字节
   (多 4 字节, 整个字面池错位)。这是本次唯一真正卡住的一点。

3. **`HPos` 不要加显式 `& 0x1FF`**: 位域宽度 9 已自动截断, 直接写 `arg0->posX - 0x10`;
   若手写 `& 0x1FF` 会额外引入 `ldr r0,[pc]; adds r0,r2,#0; ands r1,r0` 两条 (池里多一个 0x1FF 常量
   反而更远)。同理 `CharNo` 不加 `& 0x3FF`。

这三条并行改动是**互相独立**的: 任一单独代换都会让 diff 从 0 涨到 26~161 字节; 完整组合才字节一致。
